## 1. 왜 바꾸는가 (현재 문제)

### 1-1. 메뉴 관리가 어려운 진짜 이유
- 저장소(`nav_menu_items`)는 **상위-하위 2단 구조를 이미 지원**하는데, **화면에는 상위·하위를 구분하는 표시도, 하위로 만드는 방법도 없다.** 지금 있는 하위 메뉴들은 저장소에 직접 넣은 것이다.
- 화면은 순서·라벨·주소·노출 4칸짜리 납작한 표 하나뿐. 상위 메뉴와 하위 메뉴가 뒤섞여 나온다.
- 순서를 바꾸려면 숫자를 직접 입력해야 한다. 드래그 정렬 기능은 **서버에는 이미 있는데 화면에서 호출하지 않는다.**
- 새 메뉴를 추가하면 **무조건 1뎁스로만** 만들어진다(하위 지정 수단 없음).

### 1-2. 메뉴 하나가 페이지 하나가 아닌 이유
협의회 소개 드롭다운 3개가 전부 **같은 파일의 다른 위치로 스크롤만** 한다.

| 메뉴 | 실제 주소 | 결과 |
|---|---|---|
| 인사말 / 비전 | `/about.html#greeting` | 같은 페이지 상단 |
| 설립 취지 / 연혁 | `/about.html#history` | 같은 페이지 중간 |
| 조직도 / 오시는 길 | `/about.html#org` | 같은 페이지 하단 |

부작용: 어느 메뉴로 들어가도 상단 위치 표시가 **"홈 › 협의회 소개 › 인사말"로 고정**(코드에 박혀 있음). 주요 활동 2개도 동일 구조.
※ '유가족지원사업'은 단체소개가 아니라 **주요 활동 페이지** 소속이다(혼동 주의).

### 1-3. 부분 편집의 한계
페이지 뼈대(제목·영문 라벨·칸 배치)는 **코드에 박혀 있고**, 그 안의 빈칸 8개만 저장소에서 채운다.
→ 문단 추가·순서 변경·새 섹션 신설이 **구조적으로 불가능**하다. 개발자를 불러야 한다.

### 1-4. 편집기의 한계
현재 편집기는 마크다운 기반이라 **글자색·정렬·글자 크기를 원리상 지원하지 않는다.** 툴바에도 없다.
표·사진·링크까지만 가능하고, 사진 크기 조절·동영상 삽입도 안 된다.

## 2. 개편 후 그림

### 2-1. 어드민 역할 재분배

| 화면 | 개편 전 | **개편 후** |
|---|---|---|
| **메인 화면 편집** | 메뉴 + 홈 블록 + 푸터 | **메뉴 + ★페이지 통 편집 + 홈 블록 + 푸터** (화면에 관한 모든 것) |
| **콘텐츠 관리** | 공지·FAQ·활동·언론·자료실 **+ 협의회 소개 조각 편집** | **공지·FAQ·활동·언론·자료실** (글만) |

협의회 소개 탭은 제거하고 "메인 화면 편집으로 이전되었습니다" 안내 + 이동 버튼만 남긴다(통계 편집 탭이 이미 같은 방식으로 이전된 선례가 있다).

### 2-2. 운영자 작업 흐름 (핵심 시나리오)

**새 메뉴 + 새 페이지를 만들 때**
```
메인 화면 편집 → 메뉴 관리
  → [＋ 메뉴 추가] 클릭
  → 이름 입력: "후원금 사용 내역"
  → 연결 방식: ● 새 페이지 만들기   ○ 기존 페이지  ○ 주소 직접  ○ 모달  ○ 구분선
  → [만들기]
     ↳ 빈 페이지가 자동 생성되고 메뉴에 자동 연결됨 (주소 /p/donation-report 자동 부여)
  → 편집기가 바로 열림 → 글·사진·표 작성 → [임시저장]
  → 메뉴 목록에서 드래그해 "협의회 소개" 아래로 끌어놓기 → 하위 메뉴가 됨
  → [모든 변경사항 배포] → 라이브 반영
```

**기존 페이지 내용을 고칠 때**
```
메인 화면 편집 → 메뉴 관리 → 해당 메뉴 줄의 [내용 편집] 클릭 → 편집기 → 저장 → 배포
(또는 좌측 트리 '페이지 관리'에서 목록으로 찾아 편집)
```

### 2-3. 메뉴 관리 화면 (개편안)

```
┌ 메뉴 관리 ─────────────────────────────────────────────┐
│  [＋ 메뉴 추가]                    임시저장 3건  [배포] │
│                                                        │
│  ☰ 협의회 소개              연결없음    [노출●] [✎][🗑] │
│     ☰ 인사말               📄 인사말    [노출●] [✎][🗑] │
│     ☰ 주요 연혁            📄 주요연혁  [노출●] [✎][🗑] │
│     ☰ 조직도·오시는 길      📄 조직도    [노출●] [✎][🗑] │
│  ☰ 주요 활동                                           │
│     ☰ 유가족 지원사업       📄 유가족…   [노출●] [✎][🗑] │
│     ☰ 추모·장학사업         📄 추모…     [노출○] [✎][🗑] │
│  ☰ 후원 안내                🪟 후원모달  [노출●] [✎][🗑] │
│     ┈┈┈┈ 구분선 ┈┈┈┈                          [🗑] │
│     ☰ 진행 중 캠페인        🔗 /campaigns [노출●] [✎][🗑] │
└────────────────────────────────────────────────────────┘
   ☰ 를 잡고 끌어서 순서 변경 · 다른 메뉴 안으로 넣으면 하위 메뉴
   ✎ = 그 메뉴가 가리키는 페이지 내용을 바로 편집
```

- 드래그로 **순서 변경과 상위/하위 이동을 동시에** 처리 (SortableJS 중첩 그룹 — 이미 프로젝트에 도입된 라이브러리)
- 드래그를 못 쓰는 상황(라이브러리 로드 실패·키보드 조작)을 위해 **↑ ↓ ← → 버튼 병행**
- 연결 대상을 색점으로 한눈에 구분: 페이지 · 주소 링크 · 창 열기 · 연결 없음 · 구분선
- 하위의 하위(3뎁스)는 **드롭 거부** — 헤더 메뉴가 2단까지만 표시하므로 애초에 못 만들게 막는다 (화면·서버 양쪽 방어)

**무엇을 즉시 반영하고 무엇을 배포로 미루나** (구현하며 확정)

| 항목 | 반영 시점 | 이유 |
|---|---|---|
| 순서·상위 이동 | **즉시** | 상위 관계에는 임시저장 칸이 없다. 순서만 임시저장하면 '순서는 새 값·상위는 옛 값'인 반쪽 상태로 사이트에 나가 트리가 어긋난다. 순서 변경은 되돌리기 쉬워 즉시 반영이 더 안전하다 |
| 노출 켜기/끄기 | **즉시** | 급히 감춰야 할 때 배포를 기다릴 수 없다 (현행 유지) |
| 연결 대상 변경 | **즉시** | 유형이 바뀌면 관련 값들을 함께 정리해야 해 반쪽 상태가 위험하다 |
| 메뉴 이름 | 배포 필요 | 방문자가 바로 보는 문구라 실수 영향이 크다 (현행 유지) |

## 3. 저장소 설계

### 3-1. 신규 — 페이지 본체 `site_pages`

| 컬럼 | 타입 | 역할 |
|---|---|---|
| `id` | serial PK | |
| `slug` | varchar(100) UNIQUE NOT NULL | 주소 `/p/{slug}` |
| `title` | varchar(200) NOT NULL | 페이지 큰 제목 |
| `eyebrow` | varchar(100) | 제목 위 영문 라벨 (예: GREETING) |
| `subtitle` | varchar(300) | 제목 아래 한 줄 설명 |
| `content_html` | text | **발행된 본문(통짜)** |
| `draft_title` / `draft_eyebrow` / `draft_subtitle` / `draft_content_html` | 동일 타입 | 임시저장본 |
| `has_draft` | boolean NOT NULL default false | 임시저장 존재 여부 |
| `status` | varchar(20) default 'published' | `published` / `hidden` |
| `layout` | varchar(20) default 'default' | `default`(가운데 정렬 본문) / `wide`(전체폭) / `plain`(약관형) |
| `seo_title` / `seo_description` | varchar(200)/(500) | 검색 노출용. 비우면 title 사용 |
| `og_image_url` | varchar(500) | 공유 썸네일 |
| `sort_order` | integer default 0 | 페이지 목록 정렬 |
| `view_count` | integer default 0 | 조회수 |
| `created_at` / `updated_at` / `updated_by` | | |

인덱스: `slug`(unique), `status`, `has_draft`

### 3-2. 신규 — 되돌리기 `site_page_revisions`

통짜 편집은 실수 한 번에 페이지 전체가 날아간다. **자동 이력 보관은 필수 안전장치**다(Swain 미요청 항목 — 메인 판단으로 추가).

| 컬럼 | 역할 |
|---|---|
| `id` / `page_id` | |
| `title` / `eyebrow` / `subtitle` / `content_html` | 저장 직전 스냅샷 |
| `saved_at` / `saved_by` / `saved_by_name` | |
| `note` | 자동 라벨 (예: "배포 전 자동 백업") |

정책: **저장·배포 때마다 직전 상태를 자동 보관, 페이지당 최근 20개 유지**(초과분 자동 삭제). 편집기에 [이전 버전 되돌리기] 버튼.

### 3-3. 기존 확장 — `nav_menu_items` 컬럼 3개 추가

| 컬럼 | 역할 |
|---|---|
| `link_type` | varchar(20) default 'url' — `page` / `url` / `modal` / `divider` / `none` |
| `site_page_id` | integer — `link_type='page'`일 때 연결된 페이지 |
| `draft_site_page_id` | integer — 임시저장 |

기존 `href` / `opens_modal` / `css_class`는 **그대로 둔다**(하위 호환). `link_type='page'`이면 공개 렌더 시 `href`를 `/p/{slug}`로 자동 생성해 내려준다 → **주소를 사람이 관리할 필요가 없어진다.**

기존 데이터 이관: `css_class='dropdown-divider'` → `link_type='divider'`, `opens_modal` 있음 → `modal`, 그 외 → `url`.

### 3-4. 기존 `content_pages`(조각 8개)
데이터를 새 페이지로 이관한 뒤에도 **테이블은 당분간 남긴다**(되돌림 대비). 어드민 진입로만 제거. AI 비서 도구도 새 테이블을 보도록 교체.

## 4. 공개 페이지 렌더링

### 4-1. 주소 라우팅
```toml
# netlify.toml — 반드시 맨 아래 404 규칙보다 위에
[[redirects]]
  from = "/p/*"
  to = "/api/page-render?_slug=:splat"
  status = 200
  force = true
```

`api/page-render`가 하는 일 (기존 SEO 주입 함수와 같은 방식):
1. `public/page.html`(범용 뼈대) 읽기
2. 저장소에서 해당 페이지 조회 (`status='published'`, 없으면 404 페이지)
3. **제목·본문을 서버에서 미리 채워** 내려보냄 → 검색엔진 노출 + 첫 화면 깜빡임 없음
4. 검색·공유용 메타(제목·설명·썸네일) 주입
5. `?preview=1` + 관리자 로그인 → 임시저장본으로 미리보기 (기존 미리보기 체계와 동일)

`netlify.toml`의 `included_files`에 `public/page.html` 등록 필요.

### 4-2. 페이지 뼈대 `public/page.html`
헤더/푸터 슬롯 + 상단 위치표시(홈 › 상위메뉴 › 현재페이지, **메뉴 구조에서 자동 생성**) + 히어로(영문라벨·제목·부제) + 본문 영역.
`layout` 값에 따라 본문 폭만 달라진다.

### 4-3. 본문 속 특수 위젯 (숏코드)
'오시는 길'에는 지도가 들어 있다. 통짜 HTML로 옮기면 지도가 사라지므로 **자리표시 문법**을 둔다.

| 문법 | 렌더 결과 | 편집기 버튼 |
|---|---|---|
| `{{map:주소}}` 또는 `{{map:주소\|안내문}}` | 카카오맵 삽입 | [지도] |
| `{{donate}}` | 후원하기 버튼 | [후원 버튼] |
| `{{apply:support}}` | 유가족 지원 신청 버튼 | [신청 버튼] |
| `{{button:라벨\|주소}}` | 원하는 곳으로 가는 버튼 | [일반 버튼] |
| `{{modal:창키\|문구}}` | 그 밖의 창 열기 (회원가입 등) | (이관용·직접 입력) |

편집기에 전용 버튼을 달아 운영자가 문법을 외울 필요 없게 한다.

**왜 버튼을 자리표시로 바꿔야 하나** (구현하며 확인): 본문 정화가 `<button>`을 통째로 제거한다
(외부에서 붙여넣은 폼 요소 차단 목적). 따라서 기존 페이지의 신청·후원 버튼을 그대로 옮기면 사라진다.
자리표시는 정화를 **통과한 뒤** 실제 버튼으로 바뀌므로 안전하다. 이관 시 자동 치환한다.

**모르는 코드 처리**: 공개 화면에서는 조용히 지우고, 관리자 미리보기에서는 빨간 표시로 알린다.
근로계약 때 치환 안 된 `{{ }}`가 그대로 노출된 사고(2026-07-27)의 재발 방지.

## 5. 편집기 (썬에디터)

### 5-1. 도입 방식
- **기존 편집기는 건드리지 않는다.** 게시판·신고폼·활동글 8곳은 지금 편집기를 그대로 쓴다(회귀 위험 차단).
- 새 파일 `public/js/editor-page.js`(`window.SirenPageEditor`)를 만들고 **페이지 통 편집에서만** 사용한다. 안정화 후 점진 교체 여부를 재판단.
- 주소 한 줄로 불러오되 **3단 대체 경로**(jsdelivr → unpkg → cdnjs)를 둔다(기존 편집기와 동일 안전장치).
- **버전은 2.47.5로 고정**(구현하며 확정). 최신은 3.2.6이지만 폴더 구조와 옵션 체계가 바뀌었는데
  공개 문서가 부족해 동작을 확신할 수 없다. 라이브에서 편집기가 안 뜨는 사고를 피하려 검증된 2.x를 쓴다.
  저장 형식이 HTML로 같아 나중에 교체하는 부담은 작다.

### 5-2. 툴바 구성 (네이버 블로그 대응)
```
[되돌리기][다시] │ [글꼴▾][크기▾][서식▾] │ [B][I][U][S] │ [글자색][배경색]
[정렬▾][줄간격▾][목록▾][들여쓰기] │ [표][사진][동영상][링크][인용][구분선]
[지도 넣기][후원 버튼][신청 버튼] │ [HTML 보기][전체화면]
```
사진은 **끌어놓기 업로드 + 마우스로 크기·정렬 조절**을 기본 제공한다.

### 5-3. 사진 업로드
지금 쓰는 3단계 업로드 경로(주소 발급 → 저장소 직접 전송 → 확정)를 **그대로 재사용**한다. 편집기만 바뀌고 저장 경로는 동일하다. 사진은 올리기 전 자동으로 크기를 줄인다(현행 유지).

**동영상**: 현재 업로드 허용 목록에 동영상 형식이 없다. 파일 업로드 대신 **유튜브 주소 삽입**만 지원한다(용량·비용 면에서도 이쪽이 맞다).

### 5-4. 안전 정화
운영자가 저장한 HTML을 서버에서 **허용 목록 방식으로 걸러 저장**한다(`lib/sanitize-page-html.ts` 신설).
- 허용: 문단·제목·목록·표·인용·구분선·이미지·링크·글자꾸밈·`style`(색·정렬·크기·여백만)
- 차단: 스크립트, `on클릭` 류 이벤트 속성, `javascript:` 주소
- 예외 허용: 유튜브·비메오 도메인 iframe만

현재 프로젝트에는 공용 정화 모듈이 없고 자유게시판 두 곳에만 간이 처리가 있다. **이번에 공용 모듈로 만들어 이후 다른 곳도 쓸 수 있게 한다.**

### 6-1. 기존 주소 처리 (검색 노출·외부 공유 링크 보호)

**해시 없는 주소** — 서버에서 영구 이동 처리
```

/privacy.html       → /p/privacy        (301)
```

**해시가 붙은 주소** — 서버는 `#뒤`를 볼 수 없으므로 파일을 남기고 화면단에서 넘긴다
```

/about.html#history  → /p/history
/about.html#org      → /p/organization

/support.html#family    → /p/family-support
/support.html#memorial  → /p/memorial-scholarship
/support.html (해시없음) → /p/family-support
```

메뉴 저장소의 주소도 함께 갱신하고, 이후로는 **메뉴가 페이지를 직접 가리키므로 주소를 손댈 일이 없어진다.**

## 7. 작업 단계 (커밋 단위 · push는 마지막 1회)

| 단계 | 내용 | 산출 |
|---|---|---|
| **1** | 저장소 3종(페이지·이력·메뉴 컬럼) 마이그레이션 함수 + 정의 활성화 | `migrate-site-pages` → **Swain 호출 필요** |
| **2** | 페이지 관리 API (목록·상세·생성·수정·삭제·임시저장·배포·되돌리기) + 공개 조회 API | 관리자 6종 + 공개 1종 |
| **3** | 새 편집기 래퍼 + 안전 정화 모듈 + 숏코드 렌더러 | `editor-page.js`, `lib/sanitize-page-html.ts` |
| **4** | 메인 화면 편집에 **페이지 관리** 화면 추가 (목록·통 편집·미리보기·되돌리기) | |
| **5** | **메뉴 관리 전면 개편** (드래그 2단 트리 + 연결 방식 선택 + 내용 편집 연동) | 요청의 핵심 |
| **6** | 공개 렌더러 `/p/*` + 페이지 뼈대 + 위치표시 자동 생성 | |
| **7** | 9페이지 이관 마이그레이션 + 메뉴 연결 + 기존 주소 전환 | **Swain 호출 필요** |
| **8** | 콘텐츠 관리에서 소개 탭 제거 + 메뉴얼·AI 학습자료 갱신 | |

**마이그레이션 호출 2회**(1단계·7단계)만 Swain 직접 실행이 필요하고, 나머지는 자율 진행.

**푸시는 2회** (구현하며 확정 — 마이그레이션 호출이 라이브에서만 가능하기 때문)
1. **1차**: 1~7단계 전부 + 마이그 함수 2개 → 배포 → **Swain이 마이그 2회 호출** → 화면 확인
2. **2차**: 옛 주소 넘기기(리다이렉트) + 마이그 파일 삭제 + 저장소 정의 정리 + 문서

> 옛 주소 넘기기를 1차에 함께 넣지 않는 이유: 이관 결과를 확인하기 전에 옛 페이지로 못 들어가면
> 원본과 대조할 수 없다. 확인이 끝난 뒤 넘기는 것이 안전하다.

### 7-1. 저장소 정의를 켜는 순서 (중요)

메뉴 조회가 테이블의 모든 칸을 한꺼번에 가져오는 방식이라, **저장소에 칸이 없는 상태에서
정의부터 추가하면 조회가 통째로 실패해 사이트 상단 메뉴가 전부 사라진다**(CLAUDE.md §9.1.1).

그래서 이번 개편에서는 메뉴에 붙는 새 칸을 **정의 대신 직접 SQL로 다룬다**(`lib/nav-menu-links.ts`).
칸이 아직 없으면 조용히 기본값으로 넘어가므로, 저장소 준비 전에 배포돼도 사이트는 멀쩡하고
준비되는 순간 자동으로 동작한다. 페이지 본체 2종은 새 테이블이라 기존 조회에 영향이 없어 정의를 바로 켰다.
